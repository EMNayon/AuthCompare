Security fundamentals · beginner → advanced

Authentication বলছে "তুমি কে?"
Authorization বলছে "তুমি কী করতে পারো?"

দুইটা শব্দ প্রায় একই রকম শোনায়, কিন্তু system security-তে এদের role সম্পূর্ণ আলাদা। নিচের checkpoint diagram, comparison table আর real-world analogy দিয়ে concept টা একদম clear হয়ে যাবে।

AuthN → identity verify → login screen, password, OTP, biometric
AuthZ → permission check → role, scope, access rule

Rule: Authentication সবসময় Authorization-এর আগে ঘটে — identity confirm না হলে permission check করার মানেই নেই।

"তুমি কে?"

Authentication (AuthN)

  • কাজ: ব্যবহারকারীর identity verify করা
  • ঘটে: login-এর সময়, সবার প্রথমে
  • Data লাগে: credentials — password, OTP, biometric, security key
  • Fail হলে: HTTP 401 Unauthorized
  • Result: একটা verified session বা token (যেমন JWT)
  • উদাহরণ: Gmail-এ email + password দিয়ে login করা, বা fingerprint দিয়ে phone unlock
"তুমি কী করতে পারো?"

Authorization (AuthZ)

  • কাজ: verified user-এর permission/access check করা
  • ঘটে: authentication-এর পরে, প্রতিটা action-এ
  • Data লাগে: role, permission list, policy, scope
  • Fail হলে: HTTP 403 Forbidden
  • Result: নির্দিষ্ট resource access allow/deny হওয়া
  • উদাহরণ: Google Drive-এ file "view" করতে পারা কিন্তু "delete" করতে না পারা

Quick reference

Side-by-side comparison

বিষয় Authentication Authorization
QUESTION Who are you? What are you allowed to do?
ORDER প্রথমে ঘটে Authentication-এর পরে ঘটে
INPUT Username/email + password, OTP, biometric User role, permission set, resource policy
HTTP STATUS 401 Unauthorized 403 Forbidden
MECHANISM Password hashing, OTP, biometrics, SSO, MFA RBAC, ABAC, ACL, OAuth scopes, policy engine
CHANGE FREQUENCY একবার verify হলে session/token জুড়ে থাকে প্রতিটা request/action-এ আলাদা করে check হয়
REAL-WORLD ANALOGY Airport-এ passport check করা Boarding pass দেখে কোন gate দিয়ে যাবে ঠিক করা
TECH EXAMPLE Login form, Firebase Auth, Passport.js, OTP verify API Spring Security roles, Laravel Gates/Policies, JWT claims-based access
🏨💡 রিয়েল-ওয়ার্ল্ড হোটেল চেক-ইন অ্যানালজি ও লাইভ এক্সেস ফ্লো দেখতে চান?

Advanced · developer view

Request flow-এ কীভাবে কাজ করে

// Step 1 — Authentication: login → token issue

POST /api/login { "email": "user@example.com", "password": "••••••••" } // server verifies identity → issues token 200 OK { "token": "eyJhbGciOi..." }

// Step 2 — Authorization: token দিয়ে permission check

DELETE /api/projects/42 Authorization: Bearer eyJhbGciOi... // server checks role/permission for this user 403 Forbidden { "error": "insufficient_permissions" }

লক্ষ্য করো — token valid থাকা মানে user authenticated, কিন্তু তার মানে এই না যে সে সব কাজ করতে পারবে। এই যে দ্বিতীয় check, এটাই authorization layer — RBAC (role-based), ABAC (attribute-based), অথবা OAuth 2.0 scope দিয়ে implement করা হয়।

Common mistakes

Beginner থেকে advanced — যা মনে রাখা দরকার

01

401 আর 403 গুলিয়ে ফেলা — 401 মানে "তুমি কে তা জানি না", 403 মানে "তোমাকে চিনি কিন্তু access নেই"।

02

শুধু authentication দিয়ে security complete মনে করা — authorization ছাড়া logged-in যেকোনো user সব কিছু করতে পারবে।

03

Frontend-এ শুধু button hide করে authorization "implement" করা — real check সবসময় backend/server-এ হতে হবে।

04

OAuth 2.0-কে authentication protocol ভাবা — এটা মূলত authorization delegation-এর জন্য বানানো (OpenID Connect হচ্ছে authentication layer যেটা OAuth-এর উপর বসে)।

05

প্রতিটা sensitive action-এ আলাদাভাবে authorization check না করা — একবার check করেই সব জায়গায় trust করা risky।

06

Session/token expire হওয়ার পরও পুরনো permission cache-এর উপর নির্ভর করা — role change হলে token/session revalidate করা জরুরি।

Real-world analogy

Hotel check-in দিয়ে বুঝি

🧾
Check-in counter = Authentication

Reception-এ ID card দেখিয়ে প্রমাণ করছো তুমি সেই ব্যক্তি যার নামে booking করা হয়েছে। এটা identity verify করার ধাপ — এখানেই তোমার "কে তুমি" confirm হয়।

🚪
Key card = Authorization

চেক-ইনের পর যে key card পাও, সেটা শুধু তোমার নির্দিষ্ট room, gym আর pool-এ কাজ করে — অন্য কারো room-এ না। এটা define করে তুমি কোন কোন জায়গায় ঢুকতে পারবে।
